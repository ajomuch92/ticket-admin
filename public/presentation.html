Ticket Admin

Mesa de ayuda con clasificación y asignación automáticas por IA

Kimberly Geraldezca Estrada Munguía Asalia Alejandra Zavala Rodríguez Aarón Josué Montes Chicas Jorge Martín Medina Discua

Astro · Vue · Cloudflare Workers · MySQL · Workers AI · n8n

Sistema completo de tickets: portal público con asistente conversacional, API para automatización y panel de administración.

El problema

  • El soporte llega por correo, chat y de palabra: nada queda registrado.
  • Alguien tiene que leer, clasificar y repartir cada incidencia a mano.
  • El usuario no sabe en qué va su reporte.
  • Mucho de lo que llega son dudas repetidas que no necesitan un ticket.

→ Un solo canal, que filtre lo trivial y enrute el resto solo.

La propuesta

Chat de soporte El usuario cuenta su problema en lenguaje natural. La IA intenta resolverlo antes de abrir ticket.
Ticket automático Si no se resuelve, se crea solo: usuario, departamento y agente asignado sin intervención humana.
Seguimiento Código público TK-2026-0147 para consultar el estado sin necesidad de cuenta.
Panel de administración CRUD de tickets, usuarios, departamentos, estados, prioridades, roles y permisos.
API abierta POST /api/ticket permite que otros canales (n8n) creen tickets.

Stack

Astro 7 (SSR, output: server)Páginas y Actions con tipos de punta a punta
Vue 3 (islas)Solo los componentes interactivos: chat y CRUD
Cloudflare WorkersEjecución en el borde, sin servidor que mantener
HyperdrivePooling y aceleración de la conexión a MySQL
Drizzle ORMEsquema y consultas tipadas sobre MySQL
ZodValidación de toda entrada en el límite
Workers AIllama-3.3-70b-instruct-fp8-fast
Bootstrap 5UI responsiva, con modo claro/oscuro

Sin servidor propio, sin cola de mensajes, sin servicio de IA externo: todo vive en Cloudflare.

Arquitectura

Navegador / n8n → Worker (Astro SSR) → middleware
sesión + contexto de DB → Hyperdrive → MySQL
Worker → binding AI → Workers AI (Llama 3.3 70B)
  • El middleware decide quién pasa y abre la conexión solo en las rutas que tocan la base.
  • Drizzle se expone como un Proxy sobre AsyncLocalStorage: los repositorios no reciben la conexión por parámetro.
Una conexión por request; Hyperdrive hace el pooling del lado de Cloudflare.

Un camino único por capa: validador → repositorio → action/endpoint. Nada consulta la base directamente desde una página.

Modelo de datos

tickets título, descripción, id público, estado, prioridad, departamento, creador, asignado a, fechas
usuarios hash PBKDF2, activo, anónimo, departamento
departamentos unidad que atiende; base de la clasificación por IA
estados / prioridades catálogos configurables, con color
roles · permisos con sus tablas puente usuarios_roles y roles_permisos

Usuario anónimo: quien reporta desde el chat no tiene cuenta. Se crea un usuario sin contraseña e inactivo, para que el ticket tenga dueño y el mismo correo reutilice el registro.

Recorrido del usuario

/reportar
describe el problema → IA sugiere
1–3 soluciones → ¿resuelto?
sin ticket
si no → recopila nombre,
correo y detalle → confirma → ticket + código → /buscar

El primer filtro es el que más ahorra: lo trivial no llega a la cola.

El asistente

  • El system prompt fija el flujo (clasificar → sugerir → recopilar → confirmar) y el alcance: fuera de soporte, no responde.
  • Respuesta en streaming SSE: el usuario ve el texto aparecer token a token.
  • Pide confirmación explícita antes de registrar si el problema es físico o de gravedad media/alta.

¿Cómo sabe el front que ya hay datos suficientes? Un marcador al final del mensaje: 

<<TICKET>>{"nombre":"...","email":"...","titulo":"...","descripcion":"..."}

El marcador se recorta antes de pintar el mensaje: el usuario nunca lo ve; solo se muestra la tarjeta de confirmación.

POST /api/ticket

Entra lo mínimo — el endpoint resuelve el resto:

{ "nombre": "Ana", "email": "ana@ejemplo.com",
  "titulo": "No puedo entrar al correo",
  "descripcion": "Error de credenciales desde ayer" }
  1. Busca el usuario por correo; si no existe, crea uno anónimo.
  2. Asigna estado y prioridad iniciales.
  3. Clasifica el departamento con IA a partir del título y la descripción.
  4. Asigna al agente con menos tickets de ese departamento.
  5. Genera el código público y lo devuelve.
{ "id": 147, "idPublico": "TK-2026-0147" }

Clasificar y repartir

  • Al modelo se le pasa la lista de departamentos vigente y debe responder con uno; se cotejan por nombre en ambos sentidos.
  • Si el modelo falla o responde cualquier cosa, se usa el primer departamento activo: nunca se pierde un ticket por culpa de la IA.
  • El reparto es un COUNT por agente activo del departamento — gana el que menos carga tiene.
const departamentoId = await clasificarDepartamento(`${titulo}. ${descripcion}`, deps);
const asignadoAId = departamentoId
    ? await ticketsRepository.agenteConMenosTickets(departamentoId)
    : null;

Los departamentos se administran desde el panel: agregar uno cambia la clasificación sin tocar código.

Integración con n8n

Correo · formulario · WhatsApp → n8n → HTTP Request
POST /api/ticket → Ticket clasificado
y asignado
  • El mismo endpoint que usa el chat sirve para cualquier canal: una sola puerta de entrada.
  • n8n solo envía cuatro campos; no resuelve ids ni asignaciones.
  • La respuesta trae el código de seguimiento, listo para contestárselo al usuario.

Nota: el endpoint es público (lo invoca el navegador en /reportar). Expuesto a Internet, hay que ponerle Cloudflare Access o rate limiting delante.

Código de seguimiento

TK-2026-0147

  • Legible por teléfono: se dicta y se anota; un UUID no.
  • Lleva el año de creación y el id del ticket con ceros a la izquierda.
  • No expone el id interno en la URL pública de consulta.
  • Se calcula tras el INSERT (el autoincremental no existe antes) y se guarda en un UPDATE dentro del repositorio: todas las vías de creación lo heredan.
export const formatIdPublico = (id, year = new Date().getFullYear()) =>
    `TK-${year}-${String(id).padStart(4, '0')}`;

Panel de administración

  • Resumen: totales, tickets por estado y prioridad, actividad reciente.
  • Un solo componente — CrudManager.vue — sirve las siete secciones: recibe columnas, campos y el nombre del namespace de Actions.
  • Alta, edición, borrado, badges de color, truncado, paginación en cliente con tamaño de página configurable, y vista de tarjetas en móvil.
  • Acción por fila reutilizable (ej. restablecer contraseña, que devuelve una clave generada y la copia al portapapeles).

Agregar un CRUD nuevo = una página de ~30 líneas declarando columnas y campos.

Seguridad

Middleware /dashboard y las Actions privadas exigen sesión; las públicas están explícitamente listadas.
Contraseñas PBKDF2-SHA256, 100 000 iteraciones, salt por usuario. Nunca en claro.
Validación Zod en toda entrada; el endpoint público además recorta longitudes y extrae el correo.
Secretos credenciales por variables de entorno y bindings; el repositorio no lleva ninguna.
Pendiente permisos por rol aplicados en cada action, rate limiting y expiración de sesión.

  • Un solo artefacto: el Worker sirve páginas, API y estáticos.
  • El binding de IA es remoto también en desarrollo: se prueba contra el modelo real.
  • Requisito operativo: al menos un estado, una prioridad y un departamento dados de alta.

Siguientes pasos

  • SLA: fecha de vencimiento según prioridad y alerta al vencer (el campo ya existe).

  • Paginación en servidor cuando las tablas crezcan.
  • Métricas: tiempo de resolución y acierto de la clasificación por IA.
